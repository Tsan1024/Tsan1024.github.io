## 起因：不是所有内容都需要 VLM

我在处理文档解析时发现：一份 PDF 里，大量内容只是普通文本。这些内容完全没必要都交给视觉语言模型（VLM），直接使用 OCR 模型，也能获得很高的识别准确度。

于是，一个很自然的想法出现了：普通文本交给 OCR，需要更复杂识别能力的内容再交给其他模型。先分清楚要处理什么，再决定让谁来处理。

但问题恰好出在这个“分清楚”上。

## 都叫 text，却不是同一种文本

在我使用的文档解析流程中，文本段被统一标记为 `text`。一个全是普通文字的段落是 `text`，一个夹着行内公式的段落，同样也是 `text`。

对后续处理来说，这个标签还不够细。

如果直接把这些文本段交给 OCR 服务，普通文字往往识别得不错，但段落中的行内公式就容易出问题。文字读出来了，公式却没解析好，整个段落的含义也可能跟着丢失。

因此，需要解决的并不是“让所有内容都用更大的模型再识别一遍”，而是先把这个具体的问题处理好：怎样区分普通文本与包含行内公式的文本，让后续流程能够选择合适的处理方式？

## 先看看，有哪些微调方法

带着这个问题，我先调研了常见的微调方法，准备确定适合这个小任务的方案后，再充值开始实验。最初的入口是 Hugging Face 的 PEFT Quicktour：它以 LoRA 为例，介绍配置适配器、训练、保存和加载的基本流程。[[1]](#ref-1)

下面也补充了一些研究论文和官方实现作为对照。它们帮助我理解已有方法如何处理类似问题，但不代表这些方法都已在本次实验中使用或验证。

这里有两个容易混在一起的问题：**用什么目标训练，以及更新哪些参数。**

有明确输入和标准答案，可以做监督微调（SFT）；有回答之间的偏好，才需要考虑偏好优化。至于全参数微调和 LoRA，讨论的是训练时修改哪些参数。SFT 和 LoRA 并不冲突，可以组合使用。

| 方法 | 大致做法 | 这次怎么选 |
| --- | --- | --- |
| 全参数微调 | 更新模型的全部参数，训练资源开销通常较大 | 先不作为这个小预算实验的起点 |
| LoRA | 冻结原有权重，在选定层加入可训练的低秩矩阵 | 作为本次尝试的方法 |
| QLoRA | 将量化后的基座与 LoRA 结合，进一步降低基座的显存占用 | 如果显存成为瓶颈，再检查框架和模型是否支持 |

LoRA 的吸引力在于只训练一小部分新增参数，通常能减少可训练参数及其梯度、优化器状态的内存开销。但它不意味着训练一定快，也不意味着十元一定够用：基座前向计算仍然存在，输入图片大小、样本数量和训练时长都会影响成本。LoRA 原论文介绍了冻结预训练权重、训练低秩更新的思路；PEFT 文档则提供了工程实现入口。[[2]](#ref-2) [[1]](#ref-1)

对于表里的 QLoRA，PEFT 的量化指南介绍了将量化基座与 LoRA 结合的方式。它针对的是训练内存问题，不会自动解决数据标注和类别不平衡；这也是我把资源问题和效果问题分开考虑的原因。[[3]](#ref-3)

因此，这次先选 **LoRA**，并按有标注样本的监督学习思路组织任务。参数规模与训练轮数后续补充，第一版的费用记录见文末。

## 方法确定后，充 10 元做个玩具试试

确定采用 LoRA 后，我才充值了 10 元，正式开始这次模型微调尝试，看看能把这个小需求做到什么程度。

目标很具体，方法和预算也有了，接下来就看数据、训练和实际效果能不能对得上。

*本文持续更新中。目前已记录第一版微调结果和粗略费用，具体训练配置与量化评估后续补充；充值金额不等于最终训练费用。*

## 再把微调流程串起来

常见的流程可以先写成一条线：

**定义任务 → 构建数据 → 划分训练、验证和测试集 → 编写训练代码 → 小规模试跑 → 正式训练 → 测试与复盘。**

这次涉及某 OCR 服务和 LoRA，微调所用的具体模型名称不展开。

### 在服务器上找个帮手

微调过程中，除了执行训练，还会遇到问题分析和代码编写。于是，我先在服务器上安装了一个 Pi Agent，并接入 DeepSeek 作为它使用的模型，让这个帮手辅助分析问题、编写微调代码。

这里的分工是：Pi Agent 提供编程助手的工作环境，DeepSeek 为它提供分析和代码生成能力；它们辅助完成微调工作，DeepSeek 并不是这次要微调的目标模型。

这里还要分清：调用 OCR 服务和训练模型是两件事。仅有识别 API，不代表能更新服务背后的权重。执行 LoRA 需要可训练的模型及相应环境，或者服务商提供兼容的微调接口。

下面先把实施方案写清楚，具体命令和参数后续补充，第一版运行结果见文末的问题记录。

## 第一步：定义这个玩具要做什么

先把任务收窄：判断一个文本段里是否包含行内公式，帮助后续流程选择处理方式。识别出“这里有公式”，与“把公式正确转写出来”是两个不同的任务。

结合第一版结果，这个任务需要在文档区域识别中区分以下内容：

- **识别对象**：PDF 页面中的文本区域，保留文字与公式的原始视觉信息。
- **输出类别**：普通文本使用 `text`，带行内公式的文本使用 `text_with_formula`；独立公式保留 `equation` 类别。
- **用途**：普通文本继续交给 OCR，带行内公式的文本转给适合的处理流程。

第一版预测图中还保留了标题、页眉和页码等类别。这里重点关注的是 `text` 与 `text_with_formula` 的区分，而不是把整个页面简化成二分类。

## 第二步：构建训练数据

第一版的数据准备比较直接：根据 OmniDocBench 的解析结果，整理出用于训练的 JSON 数据，再接入微调流程。

转换时，关键是让原始页面或区域与对应的解析结果保持一致，并把普通文本、带行内公式的文本和独立公式的类别规则说清楚。这里的 `text_with_formula` 是本次任务使用的目标类别，不代表源数据已经提供了完全一致的标签；具体转换规则和 JSON 字段后续补充。

这种方式可以先把训练流程跑起来，但第一版有一个很明显的不足：**构建出的训练数据量有限。** 对不同版式、公式形式和容易混淆的文本，是否覆盖充分，目前还没有系统统计。仅仅把解析结果转换成 JSON，并不意味着已经得到质量足够好的训练集。

后续需要抽样检查转换后的标签，补充普通文本与公式混排的样本，并按原始文档划分训练、验证和测试集，避免相邻或近似重复的内容落入不同集合。具体数据量、类别分布和划分情况，还需要补充记录。

## 第三步：编写微调算子

这里把“微调算子”理解成一个可重复执行的训练单元：输入数据和配置，输出适配器权重、日志及评估结果，不需要从零编写底层 GPU 算子。

这个训练单元至少需要处理好几件事：

1. **加载模型和预处理器**：确认模型能接收图片，并按它要求的方式处理图片和文本。
2. **接入 LoRA**：选择与模型结构匹配的目标层，配置秩、缩放系数等参数，检查实际可训练的参数。
3. **整理批次与标签**：把样本转换为模型需要的输入格式，处理填充和损失掩码。
4. **训练与验证**：记录训练损失、验证指标、耗时和显存使用情况。
5. **保存与恢复**：保存适配器及配置，并验证重新加载后可以正常推理。

如果采用生成式输出标签，训练目标可以是让模型生成约定的类别文本，注意不要把不应学习的提示词或填充位置算入损失；如果采用分类头，就需要使用对应的分类损失，并确认分类头也参与训练和保存。具体实现取决于底座结构，不能只替换一个模型名称就认为脚本通用了。

对于支持的生成式模型，可以参考 TRL 的 SFT Trainer 文档了解数据处理、训练和验证的组织方式，是否适用仍需核对实际模型。[[4]](#ref-4)

## 第四步：先试跑，再执行微调

预算只有十元，先用少量样本走完一次流程，比直接启动长时间训练更重要。

试跑时先检查图片和标签有没有对应、损失是否正常计算、LoRA 参数是否有梯度，以及保存后的适配器能否加载。必要时可以在很小的一批样本上检查模型能否拟合，用来发现流程问题；这一步不能作为泛化效果的证明。

流程跑通后，再启动正式训练，记录学习率、有效批次大小、训练步数、输入分辨率、LoRA 配置和随机种子。根据验证集表现选择检查点，而不是只看训练损失是否一直下降。

同时设置训练步数或运行时长上限，记录平台账单。训练结束后检查计费资源是否已经停止，避免把预算花在空闲等待上。

## 第五步：测试微调，到底有没有用

测试时，用同一批未参与训练和调参的文本段，对比微调前后的结果。除了整体准确率，更关心两件事：

- **漏掉了多少带公式的段落**：这决定了还有多少公式可能被送去普通 OCR。可以看公式类的召回率。
- **误判了多少普通文本**：这决定了多少原本可以便宜处理的内容被送到了复杂流程。可以结合公式类的精确率和混淆矩阵查看。

还要把分类结果接回文档解析流程，检查公式转写质量有没有改善、额外推理延迟有多大，以及总体处理成本是否下降。分类指标变好，并不自动等于整条流水线更划算。

最后单独整理失败案例：是小字号公式看不清，还是上下标与普通文字混淆，或者换了一种文档版式就失效？这些记录会决定下一轮该补数据、改标注，还是调整方法。

*上面的训练与测试步骤用于说明实施思路，不代表各项验证都已完成。下面按问题维度记录第一版的实际进展。*

## 问题一：模型能输出新类别了吗？

第一轮先回答一个最基本的问题：经过微调，模型能不能把带行内公式的文本标成 `text_with_formula`？

第一版结果已经出来了：**模型已经支持 `text_with_formula` 类别输出，但效果还比较一般。**

图中可以看到，模型在原有的文本、独立公式等类别之外，已经能够输出 `text_with_formula`。这说明第一版已经走到了能查看预测结果的阶段，但“能输出新类别”和“能稳定分对”之间还有距离。

### 当前暴露出的不足：数据量有限

第一版使用的是根据 OmniDocBench 解析结果构建的 JSON，数据量还比较有限。这是当前已知的不足，但还不能直接把所有效果问题都归因于数据少。

接下来先整理预测错误的样本，检查 `text`、`text_with_formula` 和 `equation` 的标注边界是否一致，再有针对性地补充数据。比起立刻增加训练轮数，更想先弄清楚：模型是没见过这类内容，还是训练数据本身没有把区别表达清楚？

后续会继续按问题记录每轮修改、费用和结果，并在固定的测试集上做对比。

## 问题二：准备好的微调数据，真的可靠吗？

继续检查时，发现准备好的微调数据里存在部分 bad case。第一版效果一般，除了数据量有限，数据本身的质量也需要重新审视。

于是，又让 Pi Agent 对这些有问题的样本反复核实、修改。这个过程不是让它改完一次就结束，而是继续检查修改后的数据，对仍有疑问的地方再次核实，再做调整。

这一步也提醒了我：把解析结果整理成训练 JSON，只是完成了格式转换，并不代表每条样本都已经可靠。训练之前，需要检查数据；看到预测效果不理想时，也需要回头检查数据。

目前先记录这轮数据排查与修正。具体 bad case 的类型、修改前后的样本对比，以及修正后重新训练的效果，后续继续补充。

### 对照已有研究：先筛出可疑标注，再核实

处理标签错误也有专门的研究。Confident Learning 把关注点放在标签质量上，利用模型预测概率等信息识别和排序可疑样本，而不是默认已有标签都正确。[[5]](#ref-5)

对我当前流程的启发是：可以把“原标注与预测不一致”的样本优先送去复查。但模型和 Agent 的判断都不是标准答案，最终仍需对照原始页面及标注规则确认。我的任务还包含区域定位，不能把分类场景的方法直接当成完整的文档标注检查方案；目前也没有接入 Confident Learning。

## 问题三：数据有限，公式类还只占 19%，怎么办？

继续排查后，问题变得更具体了：不仅是总数据量有限，`text` 和 `text_with_formula` 的数量还相差四倍多。

### 先看数据分布和 v3 的表现

下面的占比只针对这两个类别，不包含 `equation` 等其他类别：

| 类别 | 块数 | 两类中的占比 |
| --- | ---: | ---: |
| `text` | 13,605 | 约 81% |
| `text_with_formula` | 3,212 | 约 19% |

按照这一轮的评估记录，当前 v3 的 `text_with_formula` 召回率为 **0.692**。在 83 页验证集中，发现两类问题：

- 32 个带行内公式的文本块被误判为 `text`。
- 29 个带行内公式的文本块直接漏检。

这里把 `text_with_formula` 简称为“公式类”，它与独立公式类别 `equation` 不同。具体匹配规则与召回率统计口径，后续随评估脚本补充。

### 是没看到，还是标签选错了？

上一轮诊断中，被误判为 `text` 的公式类块，其源文本全部包含真实的 `$...$` 公式标记。结合区域匹配结果，这批样本表现为：位置已经找到，但类别报成了普通文本。

这提示我，**类别判断偏向 `text` 可能是当前瓶颈之一**。但源文本中存在公式，并不能直接证明模型已经理解了图片里的公式；类别不平衡也还不是经过对照实验确认的唯一原因。那 29 个直接漏检的块，需要与标签误判分开分析。

另外，虽然训练损失是对参与计算的 token 求平均，也不能据此把“81% 的块是 text”直接换算成“81% 的梯度都在学 text”。不同块的输出长度、标签分词方式，以及各位置的预测误差，都会影响损失与梯度。能够确定的是，普通文本块更多，公式类标签在训练中出现的机会明显更少。

### 尝试：给公式类标签的 token 加权

这一轮准备尝试的办法，是只对目标输出中 `text_with_formula` 标签对应的 token 增加损失权重，先从 **4 倍**开始：

```text
目标输出示意：
<box:...><label:text><up>                 普通标签 token：权重 1
<box:...><label:text_with_formula><up>    公式类标签 token：权重 4
```

上面只是说明权重作用的位置。坐标、正文、结束标记以及其他类别的 token 仍使用原有权重；实际实现需要根据 tokenizer 的编码精确定位标签，不能假定一个标签字符串就是一个 token，也不能误把正文中相同的字符串加权。

对于目标为公式类标签的位置，提高交叉熵权重，就是让模型在没有给正确标签足够概率时承担更大的损失。四倍多的类别数量差提供了一个选择初始权重的参考，**但权重设为 4 并不保证类别影响被精确拉平，也不保证召回一定提高**。

实现时还要明确如何归一化。例如可以将有效目标 token 的加权损失之和，除以有效目标 token 的权重之和：

```text
loss = sum(weight[i] * cross_entropy[i]) / sum(weight[i])
```

其中只包含参与训练的有效目标位置，排除 padding 和被掩码的位置。这个写法是待验证的实现方案；相比仍除以 token 数，它有助于控制整体损失尺度的变化。最终采用哪种方式，需要与训练日志一起记录。

### 为什么不再直接对整页过采样？

上一轮 `v2aggressive` 尝试过对含公式的页面过采样，但效果不理想，出现了过多预测 `text` / `text_with_formula` 的现象。

整页过采样的问题是，公式块和同页的普通文本块会一起被重复采样，页内其他内容及布局也被同时放大。它并不能精确地只增加公式类标签的学习强度。这是对上一轮失败的一个解释，仍需结合具体采样分布核实。

token 级加权则把改动集中在公式类标签位置，避免直接复制整页。不过，**普通文本 token 的权重不变，不等于普通文本的学习完全不受影响**：各类别仍共享模型参数，提升公式类的倾向，也可能增加把普通文本误报为公式的情况。

### 对照已有方法：重加权与难例学习

类别不平衡并不是这个实验独有的问题。研究和工具中有几种相关思路，可以作为下一步的参考：

| 思路 | 已有方法如何处理 | 对本次实验的启发与限制 |
| --- | --- | --- |
| 类别加权 | PyTorch 的交叉熵支持为不同类别设置权重，文档明确将不平衡训练集列为使用场景。[[6]](#ref-6) | 支持“调整损失贡献”的思路，但我的输出是序列，需要定位标签所在的 token，而不是直接把整个词表中的某些 token 一律加权。 |
| Class-Balanced Loss | 根据每类样本的“有效数量”设计权重，考虑重复样本带来的收益递减。[[7]](#ref-7) | 提醒我类别权重不一定要直接取数量比的倒数，四倍只是起点。这篇论文也不直接证明本任务的 token 加权有效。 |
| Focal Loss | 降低容易分类样本的损失贡献，让训练更关注难例，原论文针对密集目标检测。[[8]](#ref-8) | 难例不等于少数类。如果困难来自错误标注，强调难例还可能放大噪声，需要先做好数据复查。 |

这些资料提供了可比较的处理思路，并不存在一条“公式类占 19%，就必须乘 4”的通用规则。对当前实验，我准备先验证最简单的标签加权，再决定是否值得引入更复杂的方法。

### 下一轮如何判断是否有效

先保持数据划分和其他训练配置尽量一致，对比标签权重为 1 与 4 的结果。83 页验证集用于这轮调参与诊断；最终效果仍需在独立测试集上确认。

重点记录：

- `text_with_formula` 的召回率是否高于 v3 的 0.692，精确率是否下降。
- 公式类误判为 `text` 的数量是否减少，反方向的误判是否增加。
- 直接漏检的公式类块是否减少，而不只是已有框的标签发生变化。
- 普通文本、独立公式及其他类别的检测与定位表现是否退化。

如果四倍权重带来过多误报，再用验证集比较较小的权重。这里的目标是找到召回与误报之间更合适的平衡，而不是只把某一个数字推高。

这一步处理的是有限数据中的类别不平衡，不能替代补充新样本。对于训练集中缺少的版式和公式形式，仍需要继续收集并核实数据。**目前已记录诊断结果与加权方案，重训后的效果待补充。**

## 问题四：怎么看训练曲线，判断模型有没有学好？

讨论到 loss 和训练曲线时，我发现自己对模型训练与分析这部分的认识还很欠缺。之前更多关注的是训练能不能跑通、预测图有没有输出目标标签，以及最终的召回率是多少。但训练过程中模型究竟学得怎么样，我还不太会判断。

最开始，我甚至不确定：训练曲线是不是指公式识别的准确率？

### 先分清楚，曲线里画的是什么

目前我的理解是，训练曲线并不是某一个固定指标，而是记录一个数值如何随着训练变化的图。横轴通常是训练步数（step）或训练轮数（epoch），纵轴则取决于想观察什么。

| 观察项 | 它回答的问题 |
| --- | --- |
| 训练 loss | 模型在参与训练的数据上，与目标输出的差距是否在减小？ |
| 验证 loss | 在不参与参数更新的数据上，模型的预测误差怎样变化？ |
| 公式类召回率 | 应该识别出的 `text_with_formula` 块，有多少被正确找到了？ |
| 公式类精确率 | 预测为 `text_with_formula` 的块，有多少确实正确？ |

之前记录的 v3 召回率 0.692，只是一次评估结果。如果在训练过程中定期评估，把这些结果按训练步数连起来，才能看到它的变化趋势。这里评估的仍然是区域定位和类别判断，不是公式内容的转写准确度。

### loss 下降，是否就说明效果变好了？

微调通过更新可训练参数来降低训练损失。但总 loss 汇总了多个输出位置的误差，普通文本或坐标等位置学得更好，并不保证公式类标签也同样改善。因此，我需要把 loss 和实际任务指标放在一起看。

如果训练 loss 持续下降，验证 loss 却持续上升，就需要排查是否过拟合；如果总 loss 下降，公式类召回仍然没有改善，则需要继续检查类别分布、标签质量和损失设置。这些是准备学习的分析思路，不是这次实验已经确认出现的现象。

还有一点与问题三直接相关：给公式标签加权之后，loss 的计算口径变了。加权前后的训练 loss，不能只比数值大小就判断哪个模型更好；仍然要用相同的评估数据和指标比较结果。损失权重与归约方式可结合交叉熵文档理解。[[6]](#ref-6)

### 接下来准备记录什么

我准备先保存训练日志，把训练 loss、验证 loss，以及公式类的召回率和精确率按训练步数对应起来，同时记录每次实验的数据版本、权重设置和所选检查点。

先学会回答几个具体问题：模型还在有效学习吗？是否开始记住训练样本而不能泛化？提高公式召回的同时，是否增加了普通文本误报？应该保留哪个检查点，而不只是默认最后一轮最好？

目前还没有整理出这次实验的实际训练曲线，也不能据此判断是否过拟合。这个问题先作为训练分析方面的学习记录，后续再补日志、曲线和自己的理解。

## 后续问题：目前还没有概念的方向

走到这里，还有一些想继续了解的问题，但目前还没有形成清晰的认识。先把问题记下来，等弄明白以后，再决定是否值得用到这个玩具上。

### RSI 或 RL 能不能用于这个任务？

除了目前的监督微调和标签加权，还想了解 RSI、RL 这些方向。这里先保留 RSI 这个缩写，具体指什么方法、对应哪种训练流程，还需要进一步确认；对于 RL（强化学习），也还没想清楚它在这个任务里适合解决什么问题。

接下来需要先回答几个基础问题：它们和现在的微调方式有什么区别？需要准备什么数据或反馈？如果采用 RL，怎样衡量一次输出的好坏？这些额外工作是否比继续修正标注、补充样本更有价值？

目前这里只是列出疑问，还没有选择具体方法，也没有开展相关实验。

可供后续学习的一个工程入口是 TRL 的 GRPO Trainer：它支持通过奖励函数对生成结果评分。[[9]](#ref-9) 对这个任务，我需要先想清楚奖励是否能够同时反映类别、定位和漏检，而不是只奖励输出格式正确。这是对未来实验的设想，不代表 RL 已经适合当前任务；RSI 的含义仍待确认。

### 模型能用了以后，怎样让推理更快？

另一个还没有概念的方向是推理加速。模型能够输出目标类别，只是第一步；如果要接进文档解析流程，还需要知道它处理一页要多久、消耗多少显存，以及是否值得增加这一步判断。

准备先测清楚当前流程的耗时：图片预处理、模型推理和结果后处理分别花了多久？单页响应速度和批量处理速度分别如何？确认瓶颈之后，再了解适合的加速方法。

加速时也需要同时检查识别效果和资源成本，尤其是本来就不够稳定的 `text_with_formula`。目前还没有选定推理框架或优化方案，后续会把测量结果、尝试过程和效果继续记录下来。


作为推理性能分析的入门资料，PyTorch Profiler 可以记录算子的耗时和内存使用情况，帮助定位开销。[[10]](#ref-10) 我准备借鉴这种先测量再优化的方式，再决定是否尝试批处理、量化或推理框架优化，而不是先假定换一个框架就会变快。
